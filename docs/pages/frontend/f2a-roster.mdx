# Campaign roster (F2a)

`/roster` is the first Ada-backed application page. It requests
`GET /api/campaign/roster`, decodes the response with the shared frontend
schema, and displays scoundrel and crew summaries.

The page has explicit loading, error, empty, and populated states. Scoundrel
and crew UUIDs are retained as `data-character-id` and `data-crew-id`
attributes so later detail-page slices can attach navigation without changing
the roster data contract.

## Creating a scoundrel or crew (UI-CREATE-01)

Each roster section offers a visible **Create scoundrel** or **Create crew**
action, even when its collection is empty or a search has no matches. These
are native navigation links styled as primary buttons, with visible keyboard
focus and at least 44-pixel touch targets. Import remains a separate disclosure;
you do not need to open it to create an entity.

**Create scoundrel** opens `/character/create`. The standard PC
flow allocates Talent dots using the current game settings and submits to
`POST /api/characters/pc` (`createPcCharacter`). The advanced experienced
scoundrel/NPC flow uses `POST /api/characters` (`createCharacter`).
**Create crew** opens `/crew/create` and submits to `POST /api/crews`
(`createCrew`). Successful creation navigates to the new entity's sheet, and
the entity is listed when you return to the roster.

Exhausted pagination controls remain hidden, rather than rendering as empty,
nonfunctional button-shaped boxes. The original report was most misleading
on an empty roster: creation was hidden inside Import, while author button
styles overrode the pager's native `hidden` display state. Neither create
endpoint depended on the roster being populated.

### Terminology boundary

App-owned visible text calls the entity a **scoundrel**: headings, buttons,
empty states, notices/errors, accessibility labels/titles/placeholders and
document titles use the same noun. API/backend terminology remains
`character`, including routes, operation/field names, schema kinds and DOM
selectors. Backend diagnostic prose displayed verbatim, raw JSON, JSON
pointers and player-entered names/notes are not rewritten.

The separate, explicitly authorized `tasks/CONF-WORDING-01.md` card
updates only five frozen browser expected strings to this UI terminology;
selectors, flows and all other assertions remain unchanged.

## Bounded rendering and degraded reachability (PERF-02)

At campaign scale the roster no longer maps every row into the DOM. Each
entity plate renders at most `ROSTER_PAGE_SIZE` (100) readable rows initially
and a `Show more` control reveals further batches, moving focus to the first
newly revealed row so keyboard and screen-reader users land in the new
content.

Two invariants are deliberate:

- **Counts and search describe the full result set, not the rendered
  window.** The `Scoundrels (N)` / `Crews (N)` headings always show total
  collection sizes, and search filters over every readable row's data (name,
  alias, playbook / crew type) before paging — matches beyond the rendered
  window stay discoverable.
- **Degraded rows are exempt from both paging and filtering.** A row with
  `isReadable: false` is the recovery path; it is always rendered at the top
  of its list with repair/delete controls mounted, and no query can hide it.
  Paging only ever bounds the readable bulk, so a degraded row can never be
  stranded behind a window boundary or hidden by non-matching fallback text.

The initial render is committed to ≤ `ROSTER_DOM_BUDGET_NODES` (2000) DOM
nodes at the 1000-row benchmark scale; both numbers are pinned by tests so
raising them is an explicit decision rather than drift. Announcements remain
narrowed to the single polite `.roster-status` region (window/match counts),
never a live region over the lists themselves (FV-031).
