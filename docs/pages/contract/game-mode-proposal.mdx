### 1.3 Current campaign state

There is essentially none. The campaign document is five scalar fields —
`kind`, `name`, `gameStem`, `createdAt`, `formatVersion` —
`contract/schemas/campaign.json:6-17`. It is **created once at startup and
never mutated**: `backend-ada/server/src/pitd_callback.adb:3114` (creation) →
`Initialize_Campaign`, which is explicitly "startup-only"
(`backend-ada/server/src/pitd_common.adb:518-532`, guard at `:521`), and served
read-only at `backend-ada/server/src/pitd_callback.adb:3126`. There is no
revision on it, no `If-Match` discipline, and no campaign-scoped mutation route.
Mode state therefore has no existing home and needs a new campaign-scoped,
revisioned, entity-shaped resource.

## 2. The mode model

**Proposed** (matches the brief at `docs/pages/backlog/playtest-2026-10-scoundrel.mdx:39-43`;
no source disagrees, because no source has any opinion — see §1.1):

```
mode:    free-play | score | downtime
score phases:    planning → engagement → action → end
downtime phases: payoff → heat → entanglements → activities
```

- `free-play` has **no** sub-phase (`phase: null`). It is the mode in which the
  sheet behaves exactly as it does today — the regression-safe default.
- `score` and `downtime` always have an ordered `phase` from their own fixed list.
- Advancing a phase is the only forward step; there is no free-form phase
  jumping. Proposed rule: `mode.set` may switch mode only from `free-play`, or
  from `score/end` → `downtime/payoff` (and symmetrically `downtime/activities` →
  `free-play`). Skipping Score, or starting Downtime from the middle of a Score,
  is `VALIDATION` (open question 4).
- **Incarceration is a per-scoundrel status, not a mode.** Proposed as a
  character-level field (§3.3), cleared by the downtime entanglement step
  (§5). Source disagreement: **none** — BitS has no incarceration field at all
  (§1.1), so this is a new concept, and it is backlog item 4
  (`docs/pages/backlog/playtest-2026-10-scoundrel.mdx:45-46`), not part of this
  card.

Honest caveat to carry into the contract change: sub-phases as modelled are
**bookkeeping, not mechanics**. Per `PAPERCLIPS.md:12` and `:27` PitD stays a
sheet manager; the phase order exists so the UI and the agent both know *where
in the fiction the table is*, and so specific ops can be gated — never so the
server can roll dice or decide outcomes.

## 3. Where the state lives

### 3.1 Campaign-wide, not per-character

Proposed: a new **campaign-scoped, revisioned entity** — the first one. Mode is
a property of the table, not of a scoundrel; two scoundrels in the same campaign
are in the same mode. Storing it per-character would make "are we in downtime?"
a join, and would make a single write path disagree between sheets
(`PAPERCLIPS.md:76`: "The operation API is the only way anything — agent or UI —
mutates state").

### 3.2 Resources and operations (existing contract style)

Proposed routes — op-style POST, never whole-object PUT
(`PAPERCLIPS.md:76`), envelope `OperationResult`
(`contract/schemas/operation-result.json`), standard `id`/`ifMatch`/
`idempotencyKey` parameters (`contract/openapi.yaml:1594`), 200/404/409
response set like every other op:

| Proposed route | operationId | Purpose |
|---|---|---|
| `GET /api/campaign/mode` | `getCampaignMode` | Read mode + phase + gates + `allowedOps` (§8). |
| `POST /api/campaign/ops/mode.set` | `campaignModeSet` | `{mode, phase?}`. Validates the transition. |
| `POST /api/campaign/ops/phase.advance` | `campaignPhaseAdvance` | `{}`. Moves one step; gates on outstanding per-scoundrel work. |
| `POST /api/campaign/ops/downtime.activity` | `campaignDowntimeActivity` | `{characterId, name, description}` — records one downtime activity for one scoundrel and consumes one action (§6). |
| `POST /api/campaign/ops/score.end` | `campaignScoreEnd` | The end-of-score process (§5). |
| `POST /api/campaign/ops/downtime.end` | `campaignDowntimeEnd` | The end-of-downtime process (§5). |

Why `ops/`-style and not `PUT /campaign/mode`: the single-write-path rule
(`PAPERCLIPS.md:76`) forbids a UI whole-object PUT, and every existing mutation
is a named op (`contract/openapi.yaml:863-2564`).

Storage — proposed: `{DataDir}/campaign-state.json` alongside the existing
`campaign.json`, written by the same atomic `Atomic_Write` helper used for
entities (`backend-ada/server/src/pitd_common.adb:525`), with a monotonically
increasing `revision` and `If-Match` enforcement exactly as
`PAPERCLIPS.md:123` describes. `campaign.json` itself stays frozen at its five
fields (`contract/schemas/campaign.json:6-17`) — it is created once at startup
(`backend-ada/server/src/pitd_callback.adb:3114`) and is not a mutable entity.

Proposed `campaignState` DTO (canonical shape, no nulls, no absent keys —
`PAPERCLIPS.md:206`):

```json
{
  "kind": "campaignState",
  "id": "campaign",
  "gameStem": "blades-in-the-dark",
  "revision": 7,
  "createdAt": "2026-10-06T20:00:00.000Z",
  "updatedAt": "2026-10-06T21:14:03.221Z",
  "mode": "downtime",
  "phase": "heat",
  "scoreSequence": 3,
  "downtimeSequence": 2
}
```

`scoreSequence`/`downtimeSequence` are monotonic counters so an agent can prove
*which* score ended ("end score 3"), which is cheap and unbounded-safe.

### 3.3 Per-scoundrel additions (character DTO)

Proposed, all new:

- `downtimeActivities` — canonical array of `{name, description}` items on the
  character, written by `campaignDowntimeActivity`. Per-character (not
  campaign-wide) because the activity belongs to a scoundrel, and because
  per-character snapshots/undo (`contract/openapi.yaml:818`,
  `backend-ada/server/src/pitd_ops.adb:59`) then work for free.
- `isIncarcerated` (boolean, canonical, default `false`) — the
  per-scoundrel incarceration status (§2). Written by the entanglement step,
  never derived.
- The activity **cap** is *not* stored: it is a settings integer read through
  `Settings_Int` (`backend-ada/server/src/pitd_common.adb:973-999`) and surfaced
  as a capability projection, per `PAPERCLIPS.md:193` ("derived limits …
  never persisted"). ⚠ Tension to resolve: the crew trackers *do* store their max
  (`data/games/game-settings-schema.json:490-509`; bound-checked at
  `backend-ada/server/src/pitd_normalize.adb:2761-2762`), so a stored-max
  precedent exists — open question 6.

### 3.4 Settings-driven limits only

No hardcoded maxima anywhere (`AGENTS.md:182-183`, `PAPERCLIPS.md:133, 192`).
Proposed new settings block, e.g.:

```jsonc
"DowntimeSettings": {
  "ActivityCountMax": 3,          // downtime actions per scoundrel per downtime
  "CrewHeatAtEndOfScore": 2      // still a *proposed default the GM may override*
}
```

Both names are placeholders pending the human's ruling (open question 2). The
first must be a real setting; the second is arguably GM judgment and may not
belong in settings at all — `PAPERCLIPS.md:27` forbids encoding a downtime
procedure. What is *not* negotiable: any cap is read from
`data/games/*.json` through `Pitd_Common.Settings_Int`, and the frontend reads
it from `/api/games/{stem}` (already served read-only,
`backend-ada/server/src/pitd_callback.adb:784-793`) or the capability
projection — never from a literal.

## 4. Action gating

Denial is a **domain failure at HTTP 200** with a **new error code in the
existing union** — no new HTTP status (`contract/openapi.yaml:330-339`,
`contract/schemas/operation-result.json:145-728`):

```
code: WRONG_MODE            status: 200 (domain failure family)
details: { "op": "harm.add", "allowedIn": ["free-play","score"],
           "mode": "downtime", "phase": "heat" }
retryable: false   recovery: "switch the campaign mode first, or use an op allowed here"
```

`VALIDATION` (400) stays reserved for structurally bad requests (unknown mode
string, unknown phase for the named mode). Rows marked ⚠ are **my judgement, not
ground truth** — the human should overrule freely; no source constrains them.

Notation: `FP` = free-play · `S.pl/en/ac/end` · `D.pa/he/en/ac`. "Any" = all modes.

## 5. End-of-score process

Proposed order for `POST /api/campaign/ops/score.end` (available only in
`S.end`). "Computed" = the server derives it from settings + stored state.
"Prompted" = the caller (human GM or agent) supplies the outcome; the server
never invents it (`PAPERCLIPS.md:12, 27`).

| # | Step | Computed | Prompted |
|---|---|---|---|
| 0 | Gate: mode is `score`, phase is `end`; no roster character `isRetired` | ✅ | — |
| 1 | **XP.** Playbook XP for each PC; attribute XP per action used | Track maxima and clamping — `data/games/game-settings-schema.json:450-468` (`XpTrackMaximaSetting`), already enforced by the existing `playbook-xp.add` / `attribute-xp.add` ops (`contract/openapi.yaml:1129, 1154`) | *Which* attributes earned XP and *how much* (roll = GM judgment); the default playbook award is commonly the crew Tier (`backend-ada/server/src/pitd_ops.adb` `xp.add` family) — propose as a **suggested value the caller confirms or overrides** ⚠ |
| 2 | **Payoff.** Crew coin; per-scoundrel stash gains | Clamping to `FundMaximaSetting` (`data/games/game-settings-schema.json:470-488`) and `CrewTrackerMaxima` bounds — already handled by `coin.add` / `stash.add` (`contract/openapi.yaml:2351, 2364`) | The payout amount (clock/die result). The "+2 stash at end of downtime phase" rule is prose in an ability (`data/games/blades-in-the-dark.json:415`) and stays **outside** the server ⚠ |
| 3 | **Heat.** Crew heat added; optional per-scoundrel heat | Clamp to `CrewTrackerMaxima.HeatMax` (`data/games/game-settings-schema.json:493`, enforced at `backend-ada/server/src/pitd_normalize.adb:2035`) | The heat value. Per-crew-type modifiers are prose (`data/games/blades-in-the-dark-crews.json:24`), so a settings default would be a **new** mechanical claim — proposal: do not add it; prompt every time ⚠ |
| 4 | **Entanglement roll → incarceration.** Roll; on failure set `isIncarcerated = true` for the affected scoundrel(s) | Nothing — BitS has no entanglement or incarceration model at all (§1.1) | The roll and its outcome, entirely. Recorded, never derived. |
| 5 | **Release.** Per-character `end-score` semantics: stress → 0, out-of-action flags cleared, optional `{clearArmorUsed, resetLoadoutCommitment}` | Exactly the existing contract behavior (`contract/openapi.yaml:1574-1592`; `backend-ada/server/src/pitd_ops.adb:1614-`) | The two optional cleanup flags |
| 6 | Advance to `free-play` | ✅ | — |

Atomicity and undo ⚠ — the open decision: `score.end` fans out to N characters +
M crews. Two options: (a) **per-entity snapshots**, one per affected entity, each
independently undoable, result reports per-entity outcomes — matches the existing
per-character history model (`PAPERCLIPS.md:124`); or (b) one campaign-scoped
atomic snapshot. Option (a) is proposed; the campaign `revision` still guards
mode changes. Note this is *weaker* than `/campaign/batch`'s all-or-nothing
(`contract/openapi.yaml:415`) — deliberately, so a mid-process failure does not
lose the whole score. Open question 7.

Downtime end (`downtime.end`, available in `D.ac`) is the symmetric process:
activities already recorded (§6) → **no extra compute** → advance to
`free-play`. Per-character `end-downtime` (clear session expressions +
caller-supplied vice-relief stress) is invoked or offered as today
(`contract/openapi.yaml:1647-1666`) ⚠.

## 6. Downtime action tracking

Proposed:

- One activity is one `POST /api/campaign/ops/downtime.activity`
  `{characterId, name, description}`; it appends `{name, description}` to that
  character's `downtimeActivities` and consumes one action. `name` is required
  (`minLength: 1`) and `description` is required-but-may-be-blank so the shape
  stays canonical and null-free (`PAPERCLIPS.md:206`).
- The cap is `DowntimeSettings.ActivityCountMax` from game settings (§3.4), read
  via `Settings_Int`; exceeding it is `DOWNTIME_ACTIONS_SPENT` (200, typed
  details `{count, max}`) ⚠.
- Crew cohort downtime activities (`data/games/blades-in-the-dark-crews.json:127,
  461` — "one of your cohorts may perform a downtime activity") are a **crew**
  concept and need their own record or must be explicitly out of scope ⚠ —
  open question 8. No cohort-level activity storage exists today
  (`contract/schemas/crew.json` properties: `kind … claimedClaimIds,
  claimOverrides` — no activity list).
- Removing an activity: no dedicated op is proposed. Per the single-write-path
  rule every change needs an op, so `campaignDowntimeActivityRemove {characterId,
  index}` is proposed for symmetry with `note.remove`
  (`contract/openapi.yaml:1627`).

## 7. UI — sticky mode panel

Proposed, **campaign chrome** (mode is campaign-wide, §3.1), so it must appear
on the roster and on character/crew detail, not only inside one sheet.

- **Position.** Side gutter when there is room, footer otherwise. Concretely:
  the detail sheets are centered blocks capped at `1120px`
  (`frontend/src/styles/components.css:642-644`,
  `frontend/src/styles/theme.css:58-60`), so a gutter rail only exists when the
  viewport is meaningfully wider than that block — propose a CSS-only
  container/`@media` breakpoint (the sheet already switches layout at 900px,
  `frontend/src/styles/components.css:694`) with **no** JS width probing, since
  responsive containment must be provable numerically in a real viewport
  (`AGENTS.md:161-167`).
- **Stickiness.** `position: sticky; top: var(--gutter)` in the gutter case;
  in the footer case `position: sticky; bottom: 0` as a bar under the sheet.
  Gutter and footer are the **same DOM node** re-parented by CSS, so there is
  one implementation and one set of controls.
- **Contents.** Current mode + phase, a mode switcher (three states, free-play
  default), a phase stepper (only shown for `score`/`downtime`), the activity
  counter per scoundrel, and **the two moved controls**:
  - "End score" moved **out of** `frontend/src/pages/character-sections/lifecycle.ts:16-24`
  - "End downtime" moved **out of** `frontend/src/pages/character-sections/talents.ts:190-199`
  Both become campaign-scoped invocations of `score.end` / `downtime.end` (§5).
  ⚠ Consequence to confirm: those two buttons are currently per-character. Moving
  them to a campaign panel means the campaign panel must also choose *which
  scoundrels* are included. That is a UX decision, not a mechanical one — open
  question 3. The per-character lifecycle buttons should either move wholesale
  (and gain a target picker) or stay in place as the safety valve (§4.1).
- **Backend coupling.** Gated controls render disabled with the `WRONG_MODE`
  reason in the tooltip — the same explanatory-copy obligation the lifecycle
  buttons already meet (`frontend/src/pages/character-sections/context.ts:73-75`,
  `frontend/src/pages/character-sections/stress.ts:320-324`). Nothing may be
  hidden — an agent-visible gate that the UI silently omits is a second
  convention.
- ⚠ Any implementation of this section is subject to the frontend vision gate:
  real Chromium at every affected viewport, numeric responsive evidence, and an
  independent **GPT 5.6 Luna / openai-codex / xhigh** PASS (`AGENTS.md:156-178`).
  That model has no reliable route in this sandbox, so browser evidence must be
  planned outside it.

## 8. Agent usability

Proposed — an agent must never have to guess whether an op is legal:

1. `GET /api/campaign/mode` returns mode, phase, both sequences, and:
   - `allowedOps`: the array of op names legal **right now** across the whole
     campaign (`["harm.add", "playbook-xp.add", …]`). This is the single highest
     -value field; it turns the entire §4 table into a runtime answer.
   - `nextPhases`: the legal targets from `phase.advance`.
   - `gates`: outstanding per-scoundrel work so an agent does not N+1 —
     `{characterId, blockers: ["TRAUMA_REQUIRED"] | [], activitiesRemaining, activitiesMax}`.
2. The same `allowedOps`/`mode`/`phase` fields ride on `GET /api/campaign`
   (`contract/openapi.yaml:382-384`) and on roster summaries
   (`contract/schemas/campaign.json:182-190`) so a single roster fetch answers
   "what can I do?".
3. Every `WRONG_MODE` error echoes `allowedIn`, `mode`, `phase` in `details`, so
   an agent that guessed anyway can self-correct without a second request.
4. Gating is enforced **server-side on every mutation path**, including
   `/campaign/batch` members (§4.3). `allowedOps` is a convenience projection,
   never the enforcement point (`PAPERCLIPS.md:198`: "the mutation remains
   authoritative").
5. The generated agent-skill API reference must be regenerated from the
   contract, never hand-edited (`PAPERCLIPS.md:78`, `AGENTS.md:100`).

## 9. Open questions for the human

1. **Is the three-mode / eight-sub-phase model right**, including
   `free-play` having no phase? Confirm or amend the orchestrator's proposal at
   `docs/pages/backlog/playtest-2026-10-scoundrel.mdx:39-43`.
2. **Settings name and value.** Proposed `DowntimeSettings.ActivityCountMax`.
   What is the real BitD downtime action count, and what should the key be
   called? (No downtime setting exists today — §1.2.)
3. **The two buttons.** Move "End score" and "End downtime" into the campaign
   panel entirely, or keep the per-character buttons as a safety valve and add
   campaign-scoped composites beside them? If the panel is campaign-wide, how
   does the user choose which scoundrels the score end covers — all, or a
   selection?
4. **Mode transitions.** Is `mode.set` allowed to jump (score → downtime
   directly), or only `free-play → score → downtime → free-play`? And what
   happens when a table walks away mid-score?
5. **Harm and armor timing.** Should `harm.add` be legal during
   `S.engagement` (a clock can resolve there) as proposed, or only in
   `S.action`?
6. **Stored vs derived cap.** Persist the activity cap on the character (crew
   trackers store their max — `backend-ada/server/src/pitd_normalize.adb:2761-2762`)
   or expose it only as a capability projection per `PAPERCLIPS.md:193`? And is
   the exhausted-activities error code name right?
7. **Atomicity of `score.end`.** Per-entity snapshots (each undoable, partial
   progress survives a mid-process failure) or one atomic campaign snapshot?
8. **Crew/cohort downtime activities.** In scope for this card, or a follow-up?
   Backlog item 6 asks to preload every playbook's contacts; nothing today can
   record a cohort performing a downtime activity.
9. **Playbook XP default.** Should `score.end` *suggest* the standard award (crew
   Tier) and let the caller confirm/override, or require the caller to state it
   outright? Suggesting is friendlier to an agent; requiring it keeps the server
   free of rulebook claims.
10. **Incarceration scope.** Backlog item 4 covers incarceration plus the
    start-of-downtime complications. Confirm incarceration ships as a plain
    per-scoundrel boolean set during the entanglement step — and whether
    incarceration should *block* score actions while active.
11. **Which sub-phase are heat/payoff in?** `D.heat` and `S.end` both touch crew
    heat; one mode owns it, or both? (Proposed: both, per §4.2.)
12. **Free Play semantics.** Is free-play purely "no gating", or should it also
    suppress phase display and the phase stepper entirely? (Proposed: suppress.)
