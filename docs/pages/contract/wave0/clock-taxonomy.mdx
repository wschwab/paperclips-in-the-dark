## 2. The three-concern model

Every standalone clock is fully described by three orthogonal concerns. All official categories are representable as a combination of these; no category needs its own storage type or operation family.

| Concern | Field(s) | Source of truth | Notes |
|---|---|---|---|
| Storage ownership | `ownerKind`, `ownerId` | contract | Where the clock lives and who may mutate it. `campaign` (ownerId empty), `character`, `crew`. Factions are **not** an owner kind: faction clocks are campaign-owned clocks with `purpose: faction`. |
| Narrative purpose | `purpose` | game settings (`ClockPurposes` list, §7) | Descriptive only. Paperclips never auto-resolves races, activates linked clocks, or determines fictional consequences. |
| Mechanical behavior | `behavior` | contract + settings (`RecoveryClockSize` for healing) | `bounded` (clamp at full, overflow discarded) or `rollover` (overflow carried and re-applied). |
| Descriptive relationships | `relatedClockIds` | contract | Only for racing/linked categories; descriptive, integrity rules in §9. |

## 3. Reconciled taxonomy

The official page names the umbrella concept ("a progress clock") plus seven named categories. The governing spec's purpose list adds `score` and `custom`, which are **not** named on the official page (recorded in §12, conflict B). All ten values below are the exact contract purpose values.

| # | Category | Purpose (exact value) | Ownership/kind (typical) | Mechanical behavior | Narrative behavior (official material) |
|---|---|---|---|---|---|
| 1 | Progress clock (umbrella) | `progress` | campaign, character, or crew | bounded or rollover | "Track ongoing effort against an obstacle or the approach of impending trouble." Sizes by complexity: 4 = complex, 6 = more complicated, 8 = daunting. Clock is about the obstacle, not the method. |
| 2 | Danger clock | `danger` | campaign (GM) | bounded (commonly) | GM ticks 1–3 segments on complications; when full, the danger comes to fruition (guards hunt, alarm activates). |
| 3 | Racing clock | `racing` | campaign (GM) | bounded (commonly) | Two opposed clocks; if the PCs finish first they get away, otherwise cornered; simultaneous completion resolved by fiction. Relationship is descriptive (`relatedClockIds`), never auto-resolved. |
| 4 | Linked clock | `linked` | campaign (GM; any owner possible) | bounded (commonly) | One clock unlocks another once filled (e.g. "Defense" then "Vulnerable"). Unlocking is a fiction-time GM event; Paperclips records the relationship only. |
| 5 | Mission clock | `mission` | campaign or crew (score context) | bounded (commonly) | Time-sensitive window; if the countdown runs out the mission is scrubbed or changes. |
| 6 | Tug-of-war clock | `tug-of-war` | campaign (GM; also crew turf wars) | bounded (needs emptying) | Filled *and* emptied by events; back-and-forth situations (revolution brewing, turf war). Requires a decrement path — see §10 for signed progress. |
| 7 | Long-term project | `long-term-project` | character (player project) or crew (crew project) | bounded (commonly); multi-phase = several clocks | Basic project is 8 segments; truly long-term projects span two, three, or four clocks (phases). Catch-all for unusual player goals. |
| 8 | Faction clock | `faction` | campaign (factions are world-level; not an owner kind) | bounded (commonly) | Each faction has a long-term goal; the GM ticks faction clocks during downtime; PCs may aid or interfere. |
| 9 | Score clock | `score` | crew (score ownership) | bounded or rollover | Product extension (governing spec; not named on the official page): clocks created for a score — engagement, countdowns, layered obstacles during the score. |
| 10 | Custom clock | `custom` | any | bounded or rollover | Product catch-all for anything not covered above; always available in every game setting. |

**Representability:** every category is `purpose × behavior × ownerKind/ownerId`. Racing and linked additionally use `relatedClockIds` (descriptive only). Tug-of-war needs a decrement path (signed `clock.progress`, §10) which the current API already accepts at the wire level (`segments: integer`). No category requires fictional automation or a purpose-specific operation.

## 4. Reconciliation with the C# reference models

### 4.1 What the reference models actually contain

The C# reference (`blades-in-the-sheets`) contains exactly **one concrete clock instance** in the whole tree: the character healing clock, plus the two behavior primitives.

- `ProjectClock` (bounded): `BoundedInteger` with `Min = 0`, `Max = size`; `Progress(segments)` → `ChangeUntilBound` (clamps, remainder discarded); `Ding` when full; `Reset()` → 0.
- `RolloverClock : ProjectClock`: adds `Rollover`; `Progress` stores the overflow remainder; `Reset()` = zero, then re-apply carried overflow. See §10 for the exact divergence.
- Healing clock: `Character.Monitor.MonitorHarm.HealingClock` — a `RolloverClock` embedded in character monitor state; size from `GameSetting.RecoveryClockSize` (`4` in blades-in-the-dark.json, `6` in scum-and-villainy.json); `MonitorHarm.CanHeal => HealingClock.Ding`; `Heal()` requires the clock full, resets it (rollover applied), and shifts harm intensities.
- **No standalone clock storage, no purpose concept, no clock ownership, no faction/score/crew clock model exists in the reference.** Standalone clocks are a product-level extension already present in the current contract as campaign clocks.

### 4.2 Mapping

| Axis | C# reference | Current contract | Target (this document) |
|---|---|---|---|
| Mechanical behavior | `ProjectClock` / `RolloverClock` | `clockKind: project \| rollover` | `behavior: bounded \| rollover` (rename; `project → bounded`, `rollover → rollover`) |
| Storage ownership | implicit (healing clock lives in the character monitor) | campaign only (`/clocks` = "all campaign clocks") | `ownerKind: campaign \| character \| crew` + `ownerId` |
| Narrative purpose | none | none | `purpose` from settings list (§7) |
| Relationships | none | none | `relatedClockIds` |

### 4.3 Recorded conflicts with the C# model (card Log requirement)

- **Conflict A (rollover accumulation):** `RolloverClock.Progress` *overwrites* `Rollover` with the new remainder instead of adding to it; the source carries the TODO *"edge case where calling Progress() while having Rollover could overwrite it"*. The locked decision Q24 mandates accumulation. The contract and SPARK semantics (§10) intentionally diverge from the current C# implementation; the reference's `Reset()` shape (re-apply carried overflow, at most one clock size) is preserved.
- **Conflict B (official categories):** the official page names eight categories (umbrella + 7). `score` and `custom` are not on the page; they are mandated by the governing spec. Verified against both game settings: neither game defines any clock-purpose list today (only `RecoveryClockSize`), so there is no per-game restriction to reconcile.
- **Conflict C (naming):** current contract field `clockKind` (`project`/`rollover`) is renamed to `behavior` (`bounded`/`rollover`); current `createClock` requires only `[name, clockKind, size]`. Migration mapping is explicit (§5, rule 0).

## 5. Standalone clock DTO sketch — one schema for all kinds

One schema covers campaign, character-project, crew/score, faction, and custom standalone clocks. Embedded healing clocks are **not** instances of this schema and never appear under `/api/clocks` (§6).

### Validation rules (admission; SC-C1 may encode with `if/then` where expressible)

| # | Rule | Enforced by |
|---|---|---|
| 0 | Legacy `clockKind: project \| rollover` maps to `behavior: bounded \| rollover`; legacy campaign clocks gain `ownerKind: campaign`, `ownerId: ""`, `purpose: custom` (honest catch-all for unrecorded intent), `relatedClockIds: []` — explicit legacy conversion for SC-R0/SC-C1 | canonicalizer |
| 1 | `behavior = bounded` ⇒ `rollover = 0` | admission |
| 2 | `segments ≤ size` (both behaviors) | admission |

## 6. Embedded healing clocks — why they are not `/api/clocks` rows

| Aspect | Embedded healing clock | Standalone clock |
|---|---|---|
| Storage | Nested in character monitor state: `Character.Monitor.MonitorHarm.HealingClock` (`RolloverClock`) | Own document under `/api/clocks` |
| Ownership | Implicit — the owning character; no `ownerId`, no ownership validation | Explicit `ownerKind`/`ownerId` |
| Lifecycle | Created with the character; cleared on retirement cleanup; dies with the character; no own delete endpoint | Created/updated/deleted via `/clocks` operations |
| Purpose | Recovery, implicit in the monitor — not a `purpose` value | Explicit `purpose` from the settings list |
| Behavior | Always rollover (`RolloverClock`) | `bounded` or `rollover` |
| Size | `RecoveryClockSize` from game settings (4 BitD, 6 S&V) | Any `size ≥ 1` at create |
| Operations | `/characters/{id}/ops/harm.healing-clock` (progress), `/characters/{id}/ops/harm.heal` (consumes a full clock: `CANNOT_HEAL` otherwise; resets with rollover applied; removes the named harm) | `/clocks/{id}/ops/clock.progress`, `/clocks/{id}/ops/clock.reset`, delete |
| In `/api/clocks`? | **Never.** Not listed by `listClocks`, not referenceable by `relatedClockIds`, not deletable | Yes |

Rationale: the healing clock is monitor state with a single owner, a single consumer (`harm.heal`), a settings-derived size, and no independent identity. Duplicating it into `/api/clocks` would create two sources of truth for one state machine and a second mutation path for a character-owned value. The existing character-scoped ops remain the only way to touch it.

## 8. Owner-deletion policy — **chosen: reassignment to campaign**

**Decision (frozen here, per card contract):** deleting a character or crew **reassigns** its standalone clocks to campaign ownership. The confirmation-guarded cascade is rejected (below).

### Observable behavior

- `DELETE /characters/{id}` or `DELETE /crews/{id}` (with `If-Match`) atomically, in the same snapshot that removes the owner:
  - every standalone clock with `ownerKind = character|crew` and `ownerId = <deleted id>` becomes `ownerKind: "campaign"`, `ownerId: ""`;
  - each reassigned clock gets a new `revision` and bumped `updatedAt`; its `name`, `purpose`, `behavior`, `size`, `segments`, `rollover`, and `relatedClockIds` are unchanged; its history is preserved (the reassignment is a new snapshot).
- A clock that is already campaign-owned is untouched by any owner deletion.
- Clock deletion is never a side effect of character/crew deletion — no clock disappears from `/api/clocks` unless explicitly deleted there.
- The delete `OpResult` SHOULD report the reassigned clock ids (e.g. `reassignedClockIds`) so clients can surface the change; exact result shape is SC-C2's decision.
- Failure part-way through the delete+reassign transaction rolls back atomically (single snapshot).

### Rationale

Campaign clocks are the always-present collection (Q12) and the campaign is the persistent fiction container. Reassignment is **lossless** — the clock and its history survive, the GM can re-own it manually via update, and the campaign record keeps the score/faction/project story that the deleted character or crew participated in. It also keeps owner deletion free of confirmation coupling: deleting an owner never asks "and what about N clocks?", and the delete op's precondition set stays minimal.

### Rejected alternative: confirmation-guarded cascade

Deleting an owner would require the caller to confirm, then cascade-delete the owner's clocks. Rejected because: (a) it destroys campaign history and clock documents that may outlive their owner fictionally; (b) it couples every character/crew deletion to a clock inventory check and a second confirmation dialog, adding failure modes and concurrency surface for no data-safety gain; (c) it contradicts the "deleting an owner does not silently delete its clocks" direction in the governing spec, whose stated default is reassignment. A GM who truly wants clocks gone can delete them explicitly.

## 9. Related-clock integrity — **chosen: cleanup (unlink on delete)**

**Decision:** deleting a standalone clock removes its id from every remaining clock's `relatedClockIds` in the same atomic snapshot. No dangling references can exist in readable state.

### Observable behavior

- `DELETE /clocks/{id}` atomically removes `{id}` from `relatedClockIds` of all other standalone clocks; those clocks get new revisions/`updatedAt` in the same snapshot.
- The delete never cascades to the related clocks themselves — a racing pair or linked chain is a *relationship*, not ownership; only the reference is removed.
- Because `relatedClockIds` is the only place a clock can be referenced (no other entity type references clocks; healing clocks are unreferenceable), one scan of the clocks collection is a complete cleanup.

### Rationale

The codebase already establishes unlink-on-delete precedent (deleting an unreadable crew clears readable members' `dossier.crewId`), and canonical-shape philosophy favors referential cleanliness. Cleanup keeps every read path total: no client has to filter stale ids or render "deleted clock" placeholders, and the conformance oracle can assert a simple invariant — *every `relatedClockIds` entry resolves to an existing standalone clock* — after any sequence of create/delete operations.

### Rejected alternative: documented dangling references

Keeping deleted ids and documenting that clients must tolerate them was rejected because it pushes fiction-stale references into every rendering path, makes the integrity invariant unassertable, and saves only a bounded collection scan that the product already performs in an analogous case (crew unlinking).

Validation on write (rule 5 of §5): existence of referenced clocks is checked at create/update; a referenced clock that is deleted afterwards is cleaned up by this rule; self-reference is rejected; cycles are legal (mutual racing clocks are the normal case).

## 10. Rollover semantics — accumulation and reset (SPARK contract shape)

### 10.1 State and invariants

A standalone clock's mechanical state is `(segments, rollover)` with `0 ≤ segments ≤ size`, `rollover ≥ 0`, and the derived invariant:

```
rollover > 0  ⇒  segments = size
```

### 10.2 Rules

- **Progress (positive delta, `clock.progress` with `segments > 0`):** fill visible segments; overflow adds **to existing** rollover (Q24):
  - `segments' = min(segments + n, size)`
  - `rollover' = rollover + max(segments + n − size, 0)`
- **Progress (negative delta — tug-of-war emptying):** consume carried rollover **first**, then empty visible segments, never below 0:
  - with `total = segments + rollover + n`: `segments' = min(max(total, 0), size)`, `rollover' = max(total − size, 0)`
- **Reset (`clock.reset`, rollover clocks):** apply **at most one clock size** of overflow and retain the remainder:
  - `applied = min(rollover, size)`; `segments' = applied`; `rollover' = rollover − applied`
- **Reset (bounded clocks):** `segments' = 0`; `rollover` is always 0.

The reset rule matches the C# reference exactly (`RolloverClock.Reset()` = zero, then `Progress(rollover)`, whose remainder becomes the new rollover). The progress rule deliberately diverges from the current C# implementation, which overwrites rollover (source TODO; Conflict A). Consequence: a healing clock with overflow larger than its size stays full (`CanHeal` true) after a heal, permitting an immediate further heal — same shape as the reference's acknowledged edge case, now well-defined.

### 10.3 Worked example (size 6)

| Step | Operation | Before | After | Notes |
|---|---|---|---|---|
| 1 | start | 4/6, r0 | — | |
| 2 | progress +5 | 4/6, r0 | 6/6, r3 | 4+5=9 → visible 6, overflow 9−6=3 |
| 3 | progress +2 | 6/6, r3 | 6/6, r5 | new overflow 2 **adds to** existing 3 (accumulation, Q24) |
| 4 | reset | 6/6, r5 | 5/6, r0 | applies min(5,6)=5; nothing retained |
| 5 | progress +3 | 5/6, r0 | 6/6, r2 | 5+3=8 → +2 |
| 6 | progress +7 | 6/6, r2 | 6/6, r9 | overflow may exceed one clock size |
| 7 | reset | 6/6, r9 | 6/6, r3 | applies at most one size (6); retains 9−6=3 |
| 8 | reset | 6/6, r3 | 3/6, r0 | applies remaining 3 |

API result reporting (Q23 family): `requested` = requested progress; `effective` = all accepted progress including rollover; `visibleApplied` and `overflowAdded` report the split when nonzero. Step 2: `requested 5, effective 5, visibleApplied 2, overflowAdded 3`. Step 6: `requested 7, effective 7, visibleApplied 0, overflowAdded 7`. Clear/reset ops omit numeric fields unless the contract reports the cleared amount (governing spec).

> Note on the card's placeholder arithmetic ("reset → 1/6 remaining 4"): that shape violates the derived invariant (rollover > 0 while segments < size). The semantics above follow the C# reference's `Reset()` exactly and were chosen instead; the card explicitly allowed adjusting to the chosen semantics.

### 10.4 SPARK `Post` sketch

The sketch below is the contract shape SC-O5 freezes and SC-A7 proves. It covers the signed progress path (positive = accumulation, negative = tug-of-war emptying consuming rollover first) and reset. Proof obligations for SC-A7: integer bounds on `segments + rollover + delta` (a max-rollover bound or `Natural` arithmetic), and the invariant `rollover > 0 ⇒ segments = size` as a type invariant.

```ada
-- Standalone clock mechanical state: Segments (visible, 0..Size), Rollover (carried, >= 0).
-- Type invariant: Rollover > 0 -> Segments = Size.

procedure Progress (This : in out Clock; Delta : Integer)
  with
    Post =>
      (if Delta > 0 then
         -- positive: fill visible, accumulate new overflow onto existing rollover
         (if This.Segments'Old + Delta <= This.Size then
            This.Segments = This.Segments'Old + Delta
              and This.Rollover = This.Rollover'Old
          else
            This.Segments = This.Size
              and This.Rollover = This.Rollover'Old
                  + This.Segments'Old + Delta - This.Size)
       elsif Delta < 0 then
         -- negative: consume rollover first, then empty visible, never below 0
         (let Total = This.Segments'Old + This.Rollover'Old + Delta in
          (if Total >= This.Size then
             This.Segments = This.Size and This.Rollover = Total - This.Size
           elsif Total > 0 then
             This.Segments = Total and This.Rollover = 0
           else
             This.Segments = 0 and This.Rollover = 0))
       else
         This.Segments = This.Segments'Old and This.Rollover = This.Rollover'Old);

procedure Reset (This : in out Clock)
  with
    Post =>
      -- applies at most one clock size of overflow; retains the remainder
      (if This.Rollover'Old <= This.Size then
         This.Segments = This.Rollover'Old and This.Rollover = 0
       else
         This.Segments = This.Size
           and This.Rollover = This.Rollover'Old - This.Size);
```

Bounded clocks are the same types with `Rollover` constant 0 and the positive branch's clamp (remainder discarded); the `behavior` discriminant or two types is an implementation detail for SC-A7.
