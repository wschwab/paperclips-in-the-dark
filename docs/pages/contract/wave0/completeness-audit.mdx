## Counterexample set

Four counterexample classes plus the canonical-empty baseline. All are **schema-valid** values (each is a valid instance of the property's declared type; the completeness predicates are deliberately orthogonal to schema validity, per Q10). Each value satisfies the schema (readable) while failing its predicate (incomplete), which is exactly the "canonical empty ⇒ readable and incomplete" rule from the governing spec.

| # | Class | JSON snippet (value at a locked pointer) | Schema validity | Predicate | Expected predicate outcome | Classification |
|---|---|---|---|---|---|---|
| X0 | canonical empty (baseline) | `"name": ""` | valid | `nonBlankString` | **fail** (no non-whitespace characters) | readable + incomplete |
| X1 | whitespace-only string | `"name": "   "` | valid | `nonBlankString` | **fail** (no non-whitespace characters) | readable + incomplete |
| X2 | valid zero | `"size": 0` | valid (e.g. `clock.segments` `minimum: 0`; `crew.tier` `minimum: 0`) | `positiveInteger` | **fail** (not greater than zero) | readable + incomplete |
| X3 | valid false | `"traumaPending": false` | valid (`"type": "boolean"`) | `true` | **fail** (not `true`) | readable + incomplete |
| X4 | valid empty array | `"contacts": []` | valid (`"type": "array"`, no `minItems`) | `nonEmptyArray` | **fail** (zero entries) | readable + incomplete |

Full fragments SC-O3 can use directly (each is a complete, schema-valid object containing the counterexample):

```json
{ "dossier": { "name": "" } }                       // X0 — canonical empty, readable + incomplete
{ "dossier": { "name": "   " } }                    // X1 — whitespace-only, readable + incomplete
{ "clock": { "segments": 0 } }                      // X2 — valid zero, readable + incomplete (positiveInteger)
{ "character": { "traumaPending": false } }         // X3 — valid false, readable + incomplete (true)
{ "crew": { "contacts": [] } }                      // X4 — valid empty array, readable + incomplete (nonEmptyArray)
```

Notes:

- A satisfying value (any non-whitespace character for `nonBlankString`, `1+` for `positiveInteger`, `true`, any non-empty array) flips the same entity to readable + **complete** (all other pointers satisfied).
- X2/X3/X4 exercise predicates the initial field set does not use; they exist so SC-O3 can pin the full vocabulary semantics now, and so adding a future completeness pointer that uses them cannot silently change behavior (new pointers using non-`nonBlankString` predicates require a contract change per the governing spec).
- Retirement and deadish state do not change completeness: a retired or deadish entity with a canonical empty at a locked pointer remains readable + incomplete (locked in the governing spec; SC-O3 asserts the same computation across lifecycle states).

## Clocks have no completeness list — confirmed

`contract/schemas/clock.json` (all 30 lines read) declares `required: kind, id, revision, formatVersion, createdAt, updatedAt, name, clockKind, segments, size, rollover` and no `x-requiredWhenComplete` — in fact **no schema in `contract/schemas/` contains `x-requiredWhenComplete` yet** (grep across `contract/`: zero matches); SC-C1 introduces the extension on character and crew only.

**Why:** a standalone clock's identifying configuration is mandatory at creation — `name` (string), `clockKind` (enum `project`/`rollover`), and `size` (`integer`, `minimum: 1`; a positive size is enforced by the schema itself). Successful creation therefore already guarantees the fields that would appear on a completeness list (decision Q12: "standalone clocks are canonical and complete after create"). A completeness list would be vacuous. Clocks still participate fully in canonical shape, recursive admission, import, repair, deletion, and total collection behavior (governing spec, § Completeness).

## Predicate vocabulary

Approved vocabulary (Q9). Semantics are defined against the value present at the pointer in the canonical stored document.

| Predicate | Value type required | Passes when | Fails when | Used by initial field set? |
|---|---|---|---|---|
| `nonBlankString` | JSON string | at least one character is not Unicode whitespace | empty string, whitespace-only string, any non-string | **yes — all 13 pointers** |
| `nonEmptyArray` | JSON array | array length ≥ 1 | empty array, any non-array | no |
| `positiveInteger` | JSON integer | value ≥ 1 | 0, negative, non-integer, any non-number | no |
| `true` | JSON boolean | value is `true` | `false`, any non-boolean | no |

Only `nonBlankString` is needed by the initial field set (all 13 locked pointers are strings). The other three are reserved; using them on a new completeness pointer is a contract change requiring new conformance cases (SC-O3 counterexamples X2–X4 already pin their semantics). Type mismatch (e.g. `nonBlankString` applied to a number) is a predicate failure, not a schema violation — the document remains readable (schema-valid) and the pointer is incomplete; a genuinely absent or `null` property is not a completeness question at all but a canonicality question (non-canonical → repair/degraded handling, Q10).

## Schema properties that look like completeness candidates but are intentionally NOT in the locked lists

Decision Q8 fixed the lists at maximal inclusion: the pointers above are the **complete** initial sets. The following near-miss candidates were considered and excluded; they must not be silently added later:

| Candidate (character) | Shape today | Why excluded |
|---|---|---|
| `/dossier/crewId` | `string`, pattern allows empty (`character.json:83-85`) | Empty string means "not linked to a crew" — a legitimate state; an unlinked character is still a complete sheet. |
| `/dossier/notes` | `array` of strings (`common.json#/$defs/notes`, C4 change) | Free-text notes; zero notes is legitimate. |
| `/playbook/abilities`, `/playbook/experience` | `array` / `experience` object | Zero abilities taken is a legitimate build; XP progress is not identity. |
| `/monitor/*`, `/talent/*`, `/gear/*`, `/fund/*`, `/rolodex/*`, `/session/*` | various | Game state that starts at canonical zero/empty; completeness is about identity, not advancement. |
| `/notebook` | `string` | Free-form; empty is legitimate. |

| Candidate (crew) | Shape today | Why excluded |
|---|---|---|
| `/contacts`, `/factions` | `array` (C3 change; Q4 makes them required canonical arrays) | Empty means no entries by design (Q4); an empty roster is a complete crew. |
| `/tier`, `/coin`, `/stash`, `/turf` | `integer`, `minimum: 0` | Zero is a valid game value (tier 0, no coin, no turf). |
| `/heat`, `/wanted`, `/rep` | `boundedInteger` refs | Zero is the canonical starting value. |
| `/experience` | `experience` ref | Progress, not identity. |
| `/specialAbilities`, `/upgrades`, `/cohorts`, `/claimedClaimIds`, `/claimOverrides` | `array` | Empty is a legitimate build/ownership state. |
| `/notes` | `array` of strings | Zero notes is legitimate. |

Exclusion rationale in one line each case: the canonical empty of the candidate is a **legitimate permanent state**, whereas the canonical empty of a locked pointer is a **temporary "not yet filled in" state** the sheet UI must surface as incomplete.

## SC-C1 fix flags

**No locked pointer needs an SC-C1 fix.** All 13 resolve today to required, `additionalProperties: false`-scoped string properties whose empty string is schema-valid. SC-C1 is nevertheless asked to honor these guardrails while totalizing the schemas in Wave 2:

1. **Do not add `minLength` (or a `pattern`) to any locked pointer property** — the canonical empty `""` must remain a schema-valid instance so "canonical empty ⇒ readable + incomplete" holds (Q10). Counterexample: `crew.specialAbilities[].name` already carries `minLength: 1`; if a locked name gained that constraint, `""` would become non-canonical and route to repair instead of readable-incomplete, contradicting the completeness model. (`contacts[].name`, `factions[].name`, `gearItems[].name`, `rolodex.friends[].entry` already have `minLength: 1` — none of those are locked pointers, and the distinction is intentional.)
2. **Emit `x-requiredWhenComplete` exactly on the 13 pointers above** (8 character + 5 crew), as records `{pointer, predicate}` with predicate `nonBlankString`, in a stable order (list order above). SC-C5 generators and SC-O3 depend on byte-deterministic output.
3. **Keep the pointer paths valid after totalization:** Wave 2 requires every ordinary property, but must not rename, re-nest, or re-type `dossier.name/alias/look`, `dossier.heritage/background` (`namedDescription`), `dossier.vice` (`vice`), `dossier.vice.purveyor` (`namedDescription`), `playbook.name`, or the five crew strings.
4. **Do not add a completeness list to `clock.json`** (confirmed above; SC-C1 must leave clocks without one).
5. **Watch the `/dossier/alias` special case:** alias is the one locked field that is flavor-optional in the paper game; it remains locked per Q8. No action — recorded so a future "optional alias" change is a deliberate contract decision.

## Game-settings confirmation

Field sets do **not** vary by game; only option lists vary:

- `data/games/blades-in-the-dark.json` and `data/games/scum-and-villainy.json` contain only option lists and constants: `Playbooks`, `Heritages`, `Backgrounds`, `Vices` (each with `Name`/`Description`/`Sources` — e.g. vice "Faith" with purveyor source list), `Traumas`, `Attributes`, `SharedItems`, `Thesaurus`, `RecoveryClockSize`, `ActionPointMaximum`, `FactionStatus` (plus `StartingAbility` in S&V). No entity-field definitions.
- `data/games/blades-in-the-dark-crews.json` provides `CrewTypes` with `Reputations`, `HuntingGrounds`, `Lairs`, `Upgrades`, etc. as option lists (`crew.CrewTypes[0].Reputations` is an array of names).
- Entity field shape (including the 13 completeness properties) is fixed by `contract/schemas/`; settings only supply the values a complete sheet draws from. Translation files (`français-…`, `rus-…`) are option-list translations and do not alter the field sets.

Consequence for SC-O3: one completeness case matrix serves both games; only the option lists fed into predicates differ, and the predicates themselves never consult the lists (a non-empty name is complete regardless of whether it matches a known option — the schema does not constrain locked names to option lists, e.g. `crew.reputation` is a plain string, not an enum of `Reputations`).
