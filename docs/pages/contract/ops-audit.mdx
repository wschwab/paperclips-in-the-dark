### Batch execution and history boundary (2026-10-04 correction)

`POST /api/campaign/batch` executes operations and reports item outcomes in
request order, including multiple operations on the same entity. Deadlock-free
lock acquisition sorts a separate index of entity keys; it never rearranges the
operation plan. A later operation on the same entity sees the earlier planned
state. If any item fails, none of the planned entity state, revisions, or history
is committed; the existing HTTP 200 batch envelope carries per-item outcomes.

The planner acquires **all entity locks before reading or classifying stored
DTOs**, and retains those locks through planning, pre-batch snapshots, revision
stamping, and persistence (PAPERCLIPS §4.2). Concurrent batches and single-entity
mutations therefore see the preceding committed state, not a copy captured
while another writer held the lock. `BATCH-CONCURRENCY-001/002` launch 24
synchronized requests, covering batch-only and mixed single/batch writers.

Batch `Idempotency-Key` admission reuses the create-route scope guard and the
existing shared replay store (PAPERCLIPS §7.1): lookup, execution, and successful
response storage are serialized under the method/route/key scope. Exact retries
replay the original response bytes without additional entity writes, revision
increments, or history entries; failed batches are not stored as successes.
`BATCH-IDEMPOTENCY-001..004` cover sequential and 12-way concurrent retries,
multi-entity application, independent route/key scopes, and recovery after a
failed batch. This correction introduces no new status or key/body mismatch
policy.

Single-entity and batch mutations share request admission, including clock
update ownership and relationship checks. Nonexistent owners or related clocks,
self-links, and duplicate links are rejected before mutation. Schema-valid UUID
strings alone do not prove that a referenced entity exists.

The snapshot policy follows the **composite's** `x-snapshot: true`
(`contract/openapi.yaml`, `/campaign/batch`), not the first child's snapshot flag:
each successfully changed entity gets exactly one pre-batch snapshot/history
entry labeled `campaign.batch` and one revision increment. This includes batches
made entirely of otherwise snapshot-free micro-operations, such as
`notebook.set` or `clock.progress`. Undo restores the full pre-batch entity,
including the micro-operation's state.

Unknown top-level or per-operation properties violate the batch request's
`additionalProperties: false` and return the existing HTTP 400 `VALIDATION`
syntax/shape error without writes. The batch response table currently lists only
200; declaring the standardized validation response explicitly remains a
contract documentation decision, not a contract change in this correction.

Regression evidence: `BATCH-ORDER-001`–`002`, `BATCH-CLOCK-REFS-001`–`005`,
`BATCH-SNAPSHOT-001`–`004`, and `BATCH-SHAPE-001`–`002`.


### Secondary-write and undo reference boundary (2026-10-05 correction)

Deletion claims its complete, sorted `kind/id` lock set atomically before reading
or writing any affected entity: crew deletion includes characters for crew-link
cleanup; every deletion includes standalone clocks for related-link cleanup and
character/crew owner reassignment. The same entity mutexes protect ordinary
mutations and batch writes. Atomic all-or-none acquisition prevents a deletion
from holding a partial set while waiting on a batch; candidate DTOs are read
only after their locks are held. The registry has no fixed 64-entity capacity.

A private membership gate coordinates creation and deletion while the delete
footprint is discovered. Creation repeats reference-existence admission while
holding that gate, so a new character/clock cannot materialize behind a deletion
with a deleted crew, owner, or related clock. The gate's key contains `|`, which
is outside the public path-id alphabet; it cannot alias an entity mutex.

The write audit found three secondary paths: crew-link clearing, related-clock
unlinking, and character/crew-owned clock reassignment. All now use this boundary.
Import, repair, ordinary mutation, and undo write their already-locked primary
entity; batch holds every changed entity lock, creation holds the membership
gate, and campaign initialization runs before the HTTP server starts.

Undo retains full snapshot restoration. Character/crew undo explicitly promises
that behavior and declares HTTP 404 `NOT_FOUND` (`contract/openapi.yaml` lines
823–832 and 1893–1902). Silently clearing historical links would violate that
promise. Instead, undo locks the primary entity and the snapshot's referenced
entities, selects the current newest snapshot again under those locks, and
rejects restoration if any reference no longer exists. A changing snapshot
footprint is retried only after releasing the entire set. Rejection preserves
current bytes, revision, history entries, and snapshot files.

Cross-entity references comprise character `dossier.crewId` and standalone-clock
`ownerKind`/`ownerId` and `relatedClockIds`; crew cohort/contact ids and embedded
character healing clocks are local, not external entity references. Clock undo
also reuses the ordinary clock-reference validator for owner shape, self-links,
and duplicate links: invalid definitions retain HTTP 400 `VALIDATION`; missing
targets use HTTP 404 `NOT_FOUND`. Both cases are checked before any write or
snapshot consumption.

**Open contract decision:** the pre-existing generic clock undo route has no
`/clocks/{id}/undo` operation in OpenAPI. It is intentionally retained, with the
same reference validation and missing-target 404 policy, pending a separate
contract decision. The frontend has no clock-undo caller: its clock mutation
helper is called only by progress, reset, and delete; character and crew undo
remain available. No frozen operation or response declaration was changed here.

Regression evidence: `CROSS-LOCK-001`–`008` and `UNDO-REF-001`–`006`, including
overlapping batch/delete writes, more than 64 affected clocks, create/delete
membership races, private-key isolation, historical missing-reference rejection,
valid restoration, and concurrent crew deletion/member undo.

### Shared live-document write admission (2026-10-05 correction)

`Pitd_Common.Write_Entity` is now the mandatory live-document persistence
boundary: it checks task ownership of the primary entity mutex, route identity,
the membership gate for new rows, and character/clock references. Raw
`Atomic_Write` is private to the Common body. The registry records the owning Ada
task, not merely whether a mutex is busy. The same complete delete discovery
sets prevent a referenced target from disappearing behind a primary-locked
writer; ordinary mutations are not serialized through a global write mutex.

Import apply checks references under its primary mutex before history clearing
or snapshot creation and returns the declared 400 `INVALID_ENTRY` envelope,
with property-pointer issues. Ordinary mutations reject 400 `VALIDATION` before
snapshots. Secondary deletion plans every resulting document and validates all
of them before the first write or root removal. Batch validates final documents,
not transient intermediate micro-operations, and reports a typed failed item
without committing any entity/history.

**Explicit approved repair-only exception:** confirmed repair continues to
persist its previewed normalized result, including unresolved references. Its
named `Write_Repair_Preview` primitive still enforces task-owned primary mutex
and matching identity. Frozen normalization rules do not define clearing a
schema-valid UUID because its target is absent; adding a managed crew seed
would mask that question. [Repair reference policy](./repair-reference-policy)
records the categorized issue and recommendation. No unconditional graph
invariant across repair is claimed.

That issue also records the pre-existing undeclared clock import surface beside
clock undo; no frozen route/status was added. Frontend imports are bound only to
character and crew routes (`frontend/src/api/client.ts:2025,2042`). The complete
write inventory, including startup and intentionally historical snapshot copies,
is in `tasks/REVIEW-01-WRITE-REFERENCE-ADMISSION.md`. Eleven new real-HTTP cases
cover rejected imports and post-preview target deletion, a crew-import control,
ordinary/batch dirty-document rejection, final-valid batch admission, approved
repair behavior, and all-before-first-write secondary-delete rejection.

### HTTP burst connection budget (2026-10-05 correction)

`backend-ada/server/src/pitd.adb` explicitly sets `Max_Connection => 64` at
`AWS.Server.Start`. This is the HTTP worker/connection budget, separate from the
unbounded entity-lock registry. At AWS 21.0.0's default line stack size
`16#150000#` (1,376,256 bytes), 64 line tasks reserve approximately **84 MiB** of
stack capacity, versus 6.56 MiB for the former five-line default; that is reserved
capacity, not a measurement of resident memory. More workers also mean more
scheduling and per-connection state.

The previous overload supplied only the port, so `aws-server.adb:968–993`
assigned the default five connections. AWS's zero-valued keep-alive settings
derive force/close limits as `Max_Connection * 2` / `* 4`
(`aws-config.adb:393–413`). The acceptor adds two auxiliary sockets
(`aws-net-acceptors.adb:415–432`), giving former poll-set thresholds 12/22 and
current thresholds **130/258**. The listen/back queue remains 64. Above the
force threshold, first-header and idle waits use the default two-second force
timeouts; increasing the listen backlog alone would not fix the lower shedding
threshold.

The source confirms a pre-HTTP accepted-socket shedding path:
`aws-net-acceptors.adb:283–286` removes the non-ready socket nearest its timeout
when the poll set exceeds the close threshold, and `:352–356` / `:600–607`
shut it down without generating an HTTP response. Newly accepted sockets enter
that same set with `First => True` (`:114–120`), not just previously served
keep-alive sockets. This explains a genuine transport-failure mechanism.
**There is no fixed 32-request limit**: the reported approximately-32 burst
outcome depends on readiness, pooling, and timing, not arithmetic equating the
burst size with a worker/queue count.

AWS lazily reads home/current-directory `aws.ini` and program ini files through
`Get_Current` (`aws-config.adb:343–350,437–446`); none were present in the checked
repository or default home AWS configuration location. The convenience Start
overload nevertheless overwrites `Max_Connection` with its argument/default.
The explicit setting therefore removes ambiguity for this server without a new
configuration surface, status code, transport retry, or dependency fork.

`AWS-BURST-001` uses the normal unretried HTTP client to launch **64 concurrent
batch requests**, requires an HTTP 200 response and successful operation for
every request, and checks all 64 acknowledged coin/revision increments. It does
not reduce concurrency or retry transport errors. The setting is a finite
capacity budget, not a promise of lossless overload at arbitrary concurrency.
Its failing-first five-worker control recorded **43/64 `UND_ERR_SOCKET`
failures**; after the explicit setting, the same test received **64/64 HTTP 200
successes with zero transport failures**. `tasks/REVIEW-01-CROSS-ENTITY-LOCKS-UNDO.md`
retains both observed outputs.

Source paths above are within the pinned AWS 21.0.0 release's `src/core/`
(`$HOME/.local/share/alire/releases/aws_21.0.0_57fddf8f` in the investigated
installation); the dependency version is fixed in the server's Alire manifest
and lockfile.

### REVIEW-01 regression typing (2026-10-05)

The new, nonfrozen boundary regressions now decode entity responses and
collection summaries through the existing conformance `Schemas`/`decode`
mirrors before reading revisions or collection IDs. PC allocation treats absent
playbook `DefaultActionPoints` as no default dots, leaving allocation bounds
derived from game settings. Both synchronized curl probes use inline typed
Promise executors instead of `Promise.withResolvers`, preserving their
spawn-before-body release and child cleanup on the existing TypeScript library
target. No runtime API behavior or frozen contract/test changed.

conformance `npm run typecheck` (`tsc --noEmit`) exited 0 on 2026-10-05
