# CONTRACT-05: Per-scoundrel Contacts

Contract-change card **CONTRACT-05** (human ruling 2026-08-24, binding):
individual characters get their own **Contacts** list, modeled on BitS
`Models/Characters/Rolodex.cs` / `RolodexFriend.cs` with human-approved
changes — the feature is named **Contacts** (not Rolodex), and closeness has
three levels `friend | contact | rival` with `contact` as the default for new
entries.

## Naming and provenance of the name lists

The card asked where BitS carries its contact-name lists. Findings:

- BitS `Models/Settings/Constants.cs` (`Constants.DefaultNames`) holds only UI
  label synonyms (`Alias`, `Coin`, `Bulk`) — **not** name lists.
- The real lists are **game-settings data**: every playbook in the BitS game
  JSON carries a `Rolodex` block (`PlaybookSetting.Rolodex : RolodexSetting {
  Name, string[] Friends }`, `GameSetting.cs`) — e.g. the Cutter's "Dangerous
  Friends": *Marlane, a pugilist; Chael, a vicious thug; …*.

Because BitS carries them as data (not code constants), and Paperclips already
salvaged that data verbatim (spec §2), **no new settings block was added**.
The picker source of truth is the existing
`Playbooks[].Rolodex.Friends` arrays in `data/games/*.json`, surfaced through
the existing projection `GET /api/games/{stem}/playbooks/{name}`. Duplicating
them under a new `ContactsNames` block would create a second source for the
same names; the card's conditional ("if BitS carries lists as constants, copy
them into game settings") does not trigger.

## Relationship to the former character rolodex

The card's premise ("today contacts exist only on crews") was contradicted by
the codebase: characters already carried a BitS-derived **rolodex**
(`/rolodex/friends[]` with `entry` + closeness `friend|close-friend|rival`,
ops `rolodex.add` / `rolodex.set-closeness` / `rolodex.remove`). An initial
implementation added `contacts` as a second, parallel list; the human ruling
of 2026-08-25 resolved the contradiction against that reading —
**"instead of calling it Rolodex, let's just call it 'Contacts'"** — i.e.
EVOLVE the existing surface, exactly one relationship family. The clean
cutover renamed the model field to `contacts` and replaced both the
`rolodex.*` ops **and** the parallel set with a single op family:
`contact.add` / `contact.closeness` / `contact.remove`. The old ops have no
compatibility path (rejected-decision rule).

### Value migration

The closeness vocabulary changed from `friend | close-friend | rival` to
exactly `friend | contact | rival` (`contact` = default level for new
entries). Migration is **deliberately not automatic**: a stored legacy value
(e.g. `"close-friend"`) fails ordinary decoding as needs-input rather than
being silently rewritten. Stored seeds/fixtures in this repository were
migrated in place (`close-friend` → `friend`; `friend`/`rival` unchanged).
Deployments with stored characters carrying legacy values must apply the same
one-line-per-entry rewrite before upgrade.

## DTO shape

```
contacts: Array<{ id: uuid, name: string (minLength 1), closeness: "friend" | "contact" | "rival" }>
```

- `id` is server-generated (UUIDv4, like cohorts) so clients can key rows;
  ops address entries by unique `name`.
- Names are unique within the list.
- **`contacts` is a REQUIRED canonical property** of the character schema,
  like every other current-version list: absence fails ordinary decoding
  (canonical-total rule, PAPERCLIPS.md §4.6/§6). There is **no** sparse-overlay
  exception here — `claimOverrides` item fields remain the only sanctioned
  one. Character creation emits `"contacts":[]`, and every contact op stores
  the full array.
- Error codes diverge from the crew contact ops **by ruling**: duplicate name
  and unknown name are both `VALIDATION` here (crew uses `DUPLICATE` /
  `NOT_FOUND`). All three ops declare `400 VALIDATION` and `422
  INVALID_ENTITY` responses in OpenAPI alongside `200/404/409`.

## Operations

All on `/characters/{id}/ops/`, all `x-snapshot: true`, all returning the
standard OpResult envelope with the full character:

| Op | Body | Errors | Notes |
|---|---|---|---|
| `contact.add` | `{ name }` (minLength 1) | `VALIDATION` on duplicate name | New entry gets `closeness: "contact"` |
| `contact.closeness` | `{ name, closeness }` (enum `friend\|contact\|rival`) | `VALIDATION` on unknown name | Absolute setter; no numeric family (non-numeric op omits requested/effective) |
| `contact.remove` | `{ name }` | `VALIDATION` on unknown name | |

Lifecycle: contact ops are gameplay-adjacent mutations and fall under the
retired deny-list by default (a retired character returns `RETIRED`, same as
the former `rolodex.*` family). History entries are labelled with the op id
(`contact.add`, `contact.closeness`, `contact.remove`).

## Frontend

The character-detail page gains a Contacts section: rows with closeness
badges, an add control whose suggestion list comes from the character's own
playbook rolodex names (`Rolodex.Friends` of `GET
/api/games/{stem}/playbooks/{playbook}` — free-text entry remains valid, the
list is suggestions only), a closeness cycle control
(contact → friend → rival → contact), and remove. Page tests wire-assert each
op (URL, body, If-Match).
